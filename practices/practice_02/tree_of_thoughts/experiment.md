# Tree of Thoughts

- Решение, для которого нужны альтернативы: где формировать контракт OUT-1 — в сервисе, в API-слое или в отдельном Presenter-слое.
- Критерии выбора: соответствие Context Pack (минимальность первого сценария), связность с тестами, простота внедрения, контроль проверяемости.

## Запрос

Предложи три альтернативы места формирования ответа OUT-1 с указанием плюсов/минусов и влияния на тесты. Выбери одну по критериям «минимальность первого сценария», «связность с tests_*», «простота». Верни короткое объяснение.

## Внешне описанные альтернативы

| Альтернатива | Плюсы | Минусы | Оценка по критериям |
|---|---|---|---|
| A | Шейпинг в сервисе `ReviewService.review` | Простое место изменения; легче мокать в unit/integration; меньше слоёв | Презентационная логика попадает в сервис | Высокая простота; хорошая связность |
| B | Шейпинг в API-слое | Централизация формата близко к контракту HTTP | Сервис возвращает произвольное, API должен понимать внутренности | Средняя простота; риск дублирования |
| C | Отдельный Presenter-слой | Чистая разделённость обязанностей | Новая абстракция; усложнение первого инкремента | Низкая простота для Практики 2 |

## Выбор

- Выбранная альтернатива: A — шейпинг OUT-1 в сервисе.
- Почему: минимальные изменения для первого сценария; соответствует текущим проверкам (unit проверяют структуру ответа сервиса; integration/E2E — то же).
- Как проверим: tests_unit.md и tests_integration.md уже описывают проверки структуры в сервисе и на API; ADR обновим ссылкой.
