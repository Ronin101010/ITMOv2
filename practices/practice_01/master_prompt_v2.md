### 3.2. Задача помощника

Помощник получает diff и возвращает:
1. краткое описание изменения;
2. не больше трёх рисков с файлом, строкой и доказательством;
3. список проверок, которые стоит запустить.

Решение всегда принимает человек. Помощник не может approve, merge,
менять код (SCOPE-1).

### 3.3. Правила репозитория, релевантные этому PR

- `SEC-1`: перед отправкой во внешний LLM из diff удаляются токены,
  пароли и приватные ключи.
- `API-1`: diff длиннее 20 000 символов отклоняется с HTTP 413.
- `REL-1`: внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается
  в контролируемый ответ.
- `OUT-1`: ответ содержит `summary`, массив `risks` и массив `checks`.
  В `risks` максимум три элемента с полями `file`, `line`, `evidence`, `risk`.
- `SCOPE-1`: сервис только советует; он не пишет код и не выполняет
  действия в GitHub.
- `QA-1`: риск включается в ответ, только если он подтверждён строкой diff
  или правилом репозитория.
- `OBS-1`: в лог пишутся только `request_id`, длительность и статус.
  Содержимое diff и ответа модели не логируется.

Правила про `snake_case` для таблиц БД и i18n для frontend-строк
к учебному PR не относятся и в артефакты не включаются.

### 3.4. Подтверждённые findings из P1_02

Номера строк оставлены как в `P1_02.md` — для согласованности артефактов.

| # | File | Line | Risk | Rule |
|---|---|---|---|---|
| 1 | `app/review_service.py` | 15 | Дифф уходит во внешний LLM без маскирования секретов | SEC-1 |
| 2 | `app/review_service.py` | 16 | Нет таймаута 10 с и контролируемой обработки ошибок LLM | REL-1 |
| 3 | `app/review_service.py:17` → `app/api.py:9` | — | Ответ `{"comment": ...}` не соответствует OUT-1 | OUT-1 |
| 4 | `app/api.py` | 9 | Нет проверки длины diff > 20 000 и ответа 413 | API-1 |

Дополнительные gap из P1_02:
- `payload: dict` без схемы и валидации — тело запроса не проверяется;
- нет логов и метрик (`OBS-1` по diff проверить нельзя).

### 3.5. Метрики

- Доля диффов с секретами, ушедших в LLM: 0 %.
- Доля запросов, завершившихся за ≤ 10 с: 100 %.
- Соответствие контракту OUT-1: 100 % полей `summary / risks / checks`.
- Доля диффов > 20 000 символов, принятых сервисом: 0 %.
- Доля запросов с невалидным телом, дающих 5xx: 0 %.

Не использовать VTG, IRR, WACC, CSAT.

### 3.6. Хороший и плохой примеры

Хороший:

    app/review_service.py:16 — diff отправляется во внешний LLM без удаления
    секретов, что нарушает SEC-1. Проверка: передать diff с тестовым token
    и убедиться, что в prompt осталось [REDACTED].

Плохой:

    Код можно улучшить. Добавьте тесты и обработку ошибок.

### 3.7. Что пока неизвестно

- Реальный контракт LLM-провайдера.
- Есть ли внешняя обёртка, которая маскирует секреты, ограничивает длину,
  ставит timeout.
- Как логируется сервис за пределами diff.

Не додумывай эти детали. Отражай их как gap там, где уместно.
